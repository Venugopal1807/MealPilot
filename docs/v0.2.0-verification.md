# v0.2.0 offline verification

The working tree was clean before implementation. The captured baseline ran
78 tests successfully, with 51/51 scenarios passing and 10/10 seeded faults
detected by their intended invariants. The previous report was read before any
replacement; a fresh baseline report is retained locally at
`build/v020-baseline-evaluation.json`. Baseline logs are `baseline-tests.log`
and `baseline-evaluation.log` (ignored local artifacts).

Final checks: 91 tests passed, including 13 new offline Gemini contract/API tests.
All 51 original scenarios and expectations remain unchanged and pass. Nine
separate synthetic Gemini scenarios pass. Both evaluation reports detect all ten
seeded faults by their intended invariants. No constraint, grounding, ranking,
response-contract or provider-access failures were measured. `git diff --check`
passes. The application version expectation alone changes from 0.1.3 to 0.2.0.

The adapter uses the documented Gemini generateContent REST contract and Python
urllib, adding no dependency and installing no package. Fake clients verify
request schema, text, key header, timeout, response validation, refusal and error
mapping. HTTP errors 400/401/403/429/500/503 map to 503; 408/504 and socket timeouts
map to 504. Invalid structured output and changed semantics map to 502.
There are no application retries and redirects are refused.

Independent full-text policy plus the shared semantic key rejects omitted
ingredients, swapped required/excluded ingredients, changed bounds, changed cuisine,
invented preferences, unknown mandatory clauses and ambiguous negation. It does
not trust explicit_fields as evidence. The policy expands only the reviewed
paraphrases listed in README; this milestone does not accept arbitrary English.
Contradictory ingredient constraints retain both sides and produce no matches.
The optimizer and catalog validator remain unchanged.

ASGI API smoke checks cover structured compatibility, text success, sanitized
502/503/504 parsing failures and zero provider calls following failure. Additional
tests assert zero model and provider calls on unsupported/ambiguous requests.
The loopback HTTP-server test exercises an actual socket inactivity timeout;
it does not establish a total deadline, DNS timeout or remote cancellation.

No calls were made to a real model or Swiggy. No API key was needed or inspected.
Offline fixtures are contract tests, not real-model accuracy measurements. Model
availability, live JSON-schema compatibility, quota, latency, and accuracy remain
untested. Next milestone: explicitly authorized real-model evaluation using
reviewed cases and independent expected constraints, plus adversarial expansion
of the coverage policy. The same model must not judge its own correctness.

Reproduce from the repository root (Python 3.14 with requirements installed):

```powershell
py -3.14 -B -m unittest discover -s tests -v
py -3.14 -B -m evaluation --output evaluation_report.json
py -3.14 -B -m evaluation --scenarios tests/fixtures/llm_cases.json --output llm_evaluation_report.json
git diff --check
```

If the launcher selects an environment without dependencies, replace `py -3.14`
with `.\.venv\Scripts\python.exe`. Both variants were checked during this work.
Reports include source hashes and provider-call traces and are reproducible.
The separate LLM fixture path explicitly selects a fake model client; environment
variables cannot switch evaluation to a live model. The original fault audit is
unchanged. No commits or pushes were made.
