## Labels and coverage

`tests/fixtures/live_gemini_cases.json` has 25 synthetic cases. Reference values
were agent-authored explicitly from product rules, not harvested from benchmark
model responses or the parser's output. Each case separates hard constraints, soft
preferences, acceptable outcome, clarification conditions and unsupported claims.
Parsed reference intents are built from those literal labels and schema-checked.
All 25 outcomes are cross-checked against the existing acceptance policy; boundary
values have independent literal assertions. No original expectation was changed.

Coverage includes inclusive and strict budgets; required/excluded ingredient
lists; paraphrases; negation scope; cuisine/spice preferences; contradictory
ingredients; missing and multiple budgets; optional wording; unsupported dietary,
nutrition, allergy safety and mandatory cuisine; decimal and adversarial wording.
Contradiction retains both hard constraints, consistent with no-match eligibility.
These are reviewable reference labels, **not independently human-reviewed goldens**.
User review remains necessary before treating them as a human-approved benchmark.
The requested human-authored reference-label requirement is therefore still
outstanding. Automated agreement with the parser is a compatibility check, not
independent human labelling. The audit reviewed each literal label against the
documented product rules as follows; it made no expected-value changes:

| Case | Reference and product-rule rationale |
| --- | --- |
| `inclusive` | Maximum 220; `at most` includes the boundary. |
| `strict_under` | Maximum 219; integer prices must be strictly below 220. |
| `strict_below` | Maximum 180; `below 181` is strict. |
| `strict_less` | Maximum 160; `less than 161` is strict. |

Strict fixture validation rejects missing label fields, extra facts, invalid
types, inconsistent issue/outcome pairs and conflicting clarification/unsupported
labels before confirmation or client creation. Unresolved labels can retain a
null budget and known partial facts; those facts never become an accepted intent
and are excluded from complete-intent hard-constraint precision/recall.

## Later live execution, by the user only

First review the reference labels. Configure a Gemini API key through your local
secrets process and select an available model explicitly with
`MEALPILOT_GEMINI_MODEL`. A consumer subscription does not establish API credits.
The runner reads `GEMINI_API_KEY`, `MEALPILOT_GEMINI_MODEL` and optional
`MEALPILOT_LLM_TIMEOUT_SECONDS` (default 10). No packages or SDK are needed.
It does not need `MEALPILOT_INTENT_BACKEND`; `--live` is its explicit selection.

```powershell
py -3.14 -B -m live_evaluation --live --max-calls 25 --output build/gemini-live-report.json
```

The command shows 25 synthetic cases and **15 planned requests** for the current
policy; ten cases stop locally. Type exactly `RUN 15` to authorize those requests.
There is no noninteractive confirmation bypass. `--max-calls` is mandatory and
must be 1..25; there is no implicit call budget. Smaller budgets select eligible
cases in fixture order; locally blocked cases are still measured. Unrun case IDs
are listed. Cancellation, absent credentials and invalid configuration create no
client requests. The output must be a new path; existing files are refused.
Missing parent directories are created after confirmation, so the documented
`build/` path works in a fresh checkout.

One request per eligible case, no retries. Stop on HTTP 401/403, on 402/429 (credit,
quota or rate limit, conservatively stopped), or on three consecutive attempted transport
failures. Socket timeouts count as transport failures. Reports persist after
each case, including safe failure classifications and caught interruptions. A
hard process kill can lose the in-flight result; earlier completed cases remain.
There is no automatic resume/replay. Report-write failures stop further calls.

## Metrics and interpretation

The runner invokes the real `parse_intent` boundary with `GeminiIntentParser`.
An observing client retains a response in memory long enough to decode it with
the adapter's shared decoder and compare it with reference labels. This captures
schema-valid wrong interpretations **even when the application correctly rejects
them**. It never calls a meal provider or any commerce API. Catalog validation,
grounding oracles, structured API and optimizer are unchanged and covered by the
existing offline suite. Provider counts are structurally zero in this runner;
actual rejection/non-invocation assertions remain in API tests.

Metrics retain numerators and denominators, with null values for denominator zero:

- Planned, attempted, successful response and failed transport counts. A response
  with malformed output or refusal is a successful transport response but an
  incorrect interpretation/rejection, not a transport exclusion.
- Model exact matches: all received model responses, including malformed/refused
  ones. Transport failures are excluded and reported separately.
- Hard precision/recall: equality of atomic budget, required and excluded facts
  for reference-parsed cases with received responses. A changed budget is both a
  missing reference atom and an extra predicted atom. Malformed/refused output
  has zero predicted atoms, reducing recall. Per-case omitted/changed reference
  atoms and extra counts are retained. This is exact-value precision/recall, not
  a measure of the severity of changing a bound.
- Incorrect acceptance/rejection and schema-valid semantic errors; semantic-error
  denominator is schema-valid decoded responses. Explicit-fields assertions alone
  are never evidence. There is no combined score.
- Application and policy-only match metrics, plus clarification/unsupported
  accuracy. Model clarification/unsupported denominators are zero for the current
  policy because those prompts are blocked before Gemini. Application safety
  results must never be presented as model understanding of those prompts.
- Observed client-call latency, not service-only latency or a total deadline.
  Token counts are copied only from documented nonnegative integer usageMetadata
  fields, with per-field coverage denominators; absent usage and unobserved token
  totals are null, with a zero coverage denominator. Cost is
  unavailable, not estimated from a consumer subscription or guessed prices.

Reports contain selected model, source and fixture hashes, configuration and
start time. No prompts from users, raw responses, HTTP headers, API keys or raw
exception text are written. Case IDs link results back to versioned synthetic
prompts. Live output and latency are stochastic; reproducibility means the same
versioned fixture/configuration, not guaranteed identical model responses.
Per-case scores also retain the observed outcome and the names of changed soft
preference fields; arbitrary predicted strings are not persisted.

## Compatibility and limits

Official documentation reviewed:
[Gemini overview](https://ai.google.dev/gemini-api/docs),
[Interactions overview](https://ai.google.dev/gemini-api/docs/interactions-overview),
[structured output](https://ai.google.dev/gemini-api/docs/structured-output), and
[generateContent response/usage fields](https://ai.google.dev/api/generate-content).
Google recommends Interactions for new projects but says generateContent remains
supported (rechecked against the official pages on 2026-10-29). This milestone keeps generateContent/v1beta and the existing JSON
schema/prompt. Only transport status classification and extraction of the shared
decoder were needed for safe stopping and honest measurement; no API migration.
Newer models or schema features may require different protocol support; select
a model compatible with the current adapter. Availability, live schema acceptance
and actual quotas remain unverified until a separately authorized run.
The current structured-output guide primarily shows Interactions, while the
generateContent reference still lists the adapter's legacy configuration fields.
Google documents a subset of JSON Schema and recommends application validation
for schema-valid semantic errors. Local strict schema and full-text semantic
validation remain mandatory regardless of what the server enforces.

A benchmark of 25 cases cannot establish broad English accuracy, allergy safety,
serviceability or production reliability. Fifteen eligible requests measure only
the current guarded language subset. Unrestricted model clarification behavior
cannot be measured without changing the adapter contract/policy, which this work
does not authorize. Socket inactivity limits do not establish total deadlines,
DNS deadlines or remote cancellation. Model updates can change later results.
